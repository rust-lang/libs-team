Fon: We impure macros and derive don't play well together. Fixing this will be a breaking change and I can't see how to get around it. We need to evaluate macros before passing the resulting output to derive macros.

Josh Stone: Feels there's a whole can of worms in accepting impure derive macros in general

Chris: haven't we talked about something similar

Amanieu: It was about deriving `PatialEq` on enums. It compares the discriminant first and then compares the fields.

Josh: That's linked in the issue as a similar thing: https://github.com/rust-lang/rust/issues/148423

The 8472: We don't have to use macros. We have the option to roll the change back and go back to copy specialisation. Or do as dyn instead. If we can get to the underlying behaviour where we can distinguish the types, we don't need the macro.

Fon: It would still be a big correctness bug even if it's not a soundness issue if we have impure macros in derives.

The 8472: It's a more general problem that macros don't compose with impure macros. But for this specific specialization on `TrivialClone`, we have a way to resolve the unsoundness.

Fon: I think we'll put it to P-High, not P-Critical

Amanieu: you have to go out of your way to break this and the original issues is also a P-high

Josh Stone: There's a lot of shennanigans you can do by injecting randomness into a where clause.

Fon: And someone is probably using this somewhere.

### Nominated

#### [#84908](https://rust.tf/84908) Tracking Issue for ExitStatusError

Fon: The argument is that ExitStatusError is effectively a NonZero exit code because if you have a 0, it's not an error code. Trevor proposed a few different options: https://github.com/rust-lang/rust/issues/84908#issuecomment-6341775798

Fon: I'm inclined with that `Result<(), ExitStatusError>` is the actual `ExitStatus`. Having a NonZero for the error is fine and at some point we risk overcomplicating the API by adding a lot of conversion methods.

thomcc: I think it's fine if the `Result` is what we considering the `ExitStatus`.

The 8472: the `ExitStatusExt` trait has a `FromRaw` impl and it's stable, but the `Error` is unstable. We can't change the trait but we can change the impl.

Fon: Having a `NonZero<ExitStatus>` is probably not what we want.

The 8472: That wouldn't help.

Fon: No, it would just change the API to make it clear

David: I'd drop the API and if you need your methods, you'd convert `ExistStatusError` to `ExitStatus`.

Fon: We could also add a `From<ExitCode>` for `ExitStatus`. There's a concern that you can convert to `ExitStatusError` but not back to the Result.

The 8472: There's a default impl so you can get a success

Fon: That would work.

Fon: I'm inclined to leave this nominated for next week, but we may be able to denominate this in the meantime.

#### [#164731](https://rust.tf/164731) `P-lang-drag-1` core: Stabilize `abort_immediate` as `crash`

Fon: I believe the nomination is just to make sure everyone's fine with the new name. `abort_immediate` is a bit confusing and `crash` clearer.

thomcc: I like `crash`. `die` would be a bad name, the way it works in Perl is different

Fon: Yes, that's essentially a panic. Same in PHP I believ

The 8472: `crash` is cleaner. Does this print anything or does it emit an illegal instructure?

Fon: illegal instruction

Amanieu: I'm concerned about stabliizing it now

The 8472: We have many different ways of panicking/aborting. Maybe 

Fon: Would you liket that to be a formal concern blocking the FCP?

The 8472: We should look at all the ways we want to do this long term and make sense of the combinations we want

Amanieu: Last time we discussed soometing like `abort_and_unwind`

Fon: Do we want to block the FCP for stabilizing the other methods?

The 8472: Not stabilizing, just looking at the space of possibilities

Fon: This is going to be a canonical definition of crash. This is an abort that can be in core. The normal abort requires an OS ability which isn't in core

Amanieu: you can panic in core

thomcc: This is without a callback though and can be a bit more efficient.

Amanieu: I'd like the documentation to discourage people from using this and rely on panic instead.

Fon: I think the docs have it

David: In a bunch of other languages, there's expectation that crashing shows the call stack. I'm happy to stabilize this, but I also like JOsh's suggestion `halt_and_catch_fire`

Fon: Currently docs say that you should prefer panic over crash. I think we can denominate this, but we want to provide feedback.

Amanieu: I think the only situation where this is justified is when you have a memory corruption or a situation where the panic handler is unable to function correctly.

Fon: This would also the function you'd call in `panic_immediate`

David: Would fewer people use this incorrectly if we call this `crash` or `halt_and_catch_fire`?

The 8472: My main concern is how many more flavours of crashing/aborting/panicking we'll have and to make sure the names make sense

Fon: I don't think anything else would need the name `crash`

David: It's unlikely in the standard library, but user libraries would use the word "crash" a lot

Fon: I'm going to un-nominate this

#### [rfcs#4021](https://rust.tf/rfc4021) Deprecate `std::env::{vars, args}`

Fon: The main reason is if we're asking them to split it up, they'll be filing more things anyway

The 8472: We should agree on which sorts of ACPs we want. I'd prefer small fixes on args e.g. not panicking on skip, for vars maybe a new method that eg. filters out anything that's not UTF-8. And then we may not need to deprecate it.

Fon: The author is in favour of fully deprecating them and using `args_os` and `vars_os` instead

The 8472: (there are complications here)

#### [#164473](https://rust.tf/164473) Update `PartialEq`/`PartialOrd` guarantees for comparisons to match reality

Fon: The main reason this is renominated is  because someone said `PartialOrd` being `PartialEq` was surprised. And we didn't describe the axioms properly. For `PartialOrd` we define it in terms of less than because we don't require reflexivity.

Fon: I think we want to say that an ordering of this implementation is wrong. https://github.com/rust-lang/rust/issues/164184#issuecomment-6115657324 They were saying that within the definition of partial ord this is valid and we should say that it's not.

David: Is that substitutable within the same type or cross type as well?

Fon: The only cross-type we guarantee is for partialeq symmetry.

David: I'm on board with substitutability within the same type

Fon: The initial axioms were not correct. What we're proposing is stricter in terms of the axioms we're providing but weaker because we don't make guarantees across types (Fon goes into a lot of detail here that's all described in the issue)

Josh Stone: I feel the whole issue is a very pedantic reading of what we're saying. And you can't rely on anything there for unsoundness. But yes, let's shore up the definition

Fon: The main issue is removing cross-type compatibility. E.g. for Strings and Paths

The 8472: We can also declare the impl buggy

Fon: It's been there since 1.0

The 8472: But we can still say that's wrong.

Fon: there are multiple ways we can go about this
