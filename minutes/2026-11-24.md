Josh: I'd suggest we start FCP on that stabilisation PR and move on.

Josh: There was also some back-and-forth about whether using pid or some process group type. I replied that we have precedent from rustix that uses one type for pid that uses for kill and kill_group

Trevor: Should we return an error rather than quietly doing nothing if the group leader has exited already? I think so.

fon: We do have precedent for errors not being critical errors: e.g. the interrupted IO error kind.

Josh: Do we currently silently do nothing on `.kill()`?

Trevor: Yes, but that's only if the process has exited already (there's nothing you can do).

fon: If you're killing the group on behalf of the process that's already exited, that won't kill the other processes.

Trevor: yes. You don't know if the PID has been reused

The 8472: The parent process might spawn multiple children and know there are additional children still alive in the group.

fon: The issue is: if you have a single process and it exited, it's unambiguous what happened. But if you have a process group, you need to do additional checking whether the entire group exited or just that process. And for that it would be useful to send a message, so the caller can decide what to do there. They may have the information

Josh: Because the API is opaque and using whatever's internal child. We're going to only use PID on platforms that don't have anything better. On those platforms, you call `kill`, pass it negative PID and if you get an error from the kernel, you return the error.

Josh: child_kill and child_kill_group should just make the underlying system call and return the error you report the error

Trevor: But if the PID was reused, you kill some other process. And we go through some hoops to protect you from this

Josh: I wasn't aware we had any logic beyond just killing the PID

fon: I think we have consensus.

Josh: I looked it up and `kill(-PID)` on a process will actually work even after the group leader exits. Process group leaders will not be reused as PIDs as long as they're process group leaders. Looks like there is a way to do this right, we need to figure out whether that's possible.

Josh: my proposal: I think we should make `kill_process_group` wait on the process and return an error. In the future if we want to keep the ability to kill the process group, have a way to say you want this to be a process group leader, give you a way method to wait on the process without ripping it. You can get an exit status of the process but it will wait around because it's children haven't been killed yet. And then you can kill the whole group.

Trevor: Sounds good to me. We already have some of the info -- we know when the process is a group leader.

Josh: Do we have a way for setting a group leader?

Trevor: Yes, same as unix API, you call the group with the magic value `0`.

The 8472: We have the unstable `pid_fd` API. This could be used to kill the process group afterwards. Do we want to support that, or add the extra API?

Josh: If we have a `pid_fd`, we should allow you to do all those things. Right now you have to poll to get it.
