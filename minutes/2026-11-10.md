#### [#165474](https://rust.tf/165474) Regression: Removing the sealing supertrait of `SliceIndex` was a breaking change (despite `impl(self)`)

Nia: the ask is to prioritise this. How much do we care about these kinds of breakages? Based on the zulip discussion it seemed we didn't realise this would be breaking.

Josh: That's accurate, we didn't know.

Nia: There doesn't seem to be downstream code affected by this.

Fon: The breakage is limited because it's an unstable trait. You can't mention the trait or its methods without using a feature flag. Referencing the methods is required for the trait to implement.

Fon: We don't know how to track how we're going to help the ecosystem. Max already wrote a lint.

Josh: And I want to make sure Predrag is on it.

Nia: I talked to him about it. He's aware.

Nia: This particular thing is P-low/medium if there's no breakage. But we should give a pass over this class breakages.

Fon: That's the lint Max did for Clippy. It's up for review.

Fon: We could close this regression as wontfix and open a tracking issue to look at these sorts of issues.

Josh: This is a good case study for needing a language feature for sealing the trait. The lang team discussed whether we needed one at all. The author of this seems to be open to changing their crate. But we'll need to crater run this.

Fon: Would we do a crater run for reverting back to a sealed trait and see what it fixes?

Josh: Did this not get caught when we did the crater run for the release that shipped this change?

Nia: That was 1.97. The fact that we haven't caught this since then until now sounds like it's not too prevalent.

Josh: How did we miss this in 1.97 though?

Fon: Maybe nobody encountered it.

Nia: I propose putting P-High to figure out why we didn't catch this. But say that this change is acceptable breakage and let's get the clippy merged. And we can make an API guideline for this.

Fon: We could have a tracking issue for to go through the stable library, see if there are sealed traits without impl restrictions and see if we could trigger this issue by switching impl restrictions.

Nia: I left the comment.

### [#165767](https://rust.tf/165767) `Box<T, A>` becoming generic in `A` interactions with fundamentalness (over `T`) still problematic?

Frank: I'd like to bring this up to the team

Nia: I'll triage this, it's useful to have the issue. But this was considered and the consensus was that this seems fine. Thank you for opening the issue for it.

Fon: I remember most of the fundamental property stuff was figured out already. This isn't something we need to worry about for the 1.100 release, right?

Nia: No.

Nia: The consensus that the wg-allocators people had was: whenever we get specialization this will all get fixed anyway.

Frank: I'm generally sceptical of specialisation as a solution.

Nia: Of the two potential proposals there were arguments for both, and we can have our cake and eat it in the future. Messing with how fundamental works in the standard and having Box be an extra magic type is probably more risky.

Frank: With the introduction of the new allocator, you're introducing a whole new family of fundamental types. Where was this discussed?

Josh: We talked about it in the meetings where we discussed stabilizing the allocators.

Nia: It's also in the wg-allocators Zulip channel and we extensively discussed this with Amanieu at RustConf, but we didn't have notes from that. Thank you for bringing it up, this should have been written down.

Frank: Do you know whether the "we'll handle this in the future" will consider something like a FCW against these impls?

Nia: I'd like these impls to be allowed for performance reasons. If you're doing funky impls on box with custom allocators, that's because you know the allocator or have tight performance requirements.

Josh: Doesn't the use of fundamental here mean more than one crate can define the impl and there's risk diverging?

Nia: The actual type has to be local.

Josh: So you can't do this for a foreign type with local allocator?

Nia: No, that's not allowed.

Josh: Then I'm okay with this.

Fon: This follows the coherence rules

Frank: It's already the case that a lot of blanket impls already can cause breaking change if you add them even besides this. Also, all orphan rules are considered to be more limiting than what we'd like. Once we relax them, the picture could be different.

Fon: We've now introduced new problems for loosening the orphan rule by adding these impls. We are following the current rules and if we're to extend these, we'd need to consider those. But that's something the types team would have to figure out.

#### [libs#923](https://rust.tf/libs923) ACP: add `Duration` extractors for units larger than the second

Nia: Given the precedent, I think I'm in favour of this.

Fon: Jacob nominated this as the maintainer of the time crate.

Fon: Barring bikeshedding about method names, this seems to me like we should have it.

Josh: There's a long discussion in the thread on whether we should have the day and week versions given length of the day is not fixed given DST. I'm inclined to agree with the principle on day and week there but I wonder whether we should allow them anyway and add a caveat that this will not necessarily be precise.

The 8472: We have the other ACP with the constants for week etc. anyway. If we have that, we should have this too.

Josh: We also have `from_days` so having this makes sense and we should add documentation

Fon: The other potential issue would be if we added months which are regularly different duration. But days and weeks I think is fine.

Nia: We have constants of most of these things. We should be aware that these aren't perfectly fixed, but this is a reasonable definition that 1 day is 24 hours, a week is 7 days. We should note in the documentation that this is a simple numerical conversion, but I'm open to this.

David: Jacob's comment says that he thinks BurntSushi would be opposed.

Josh: BurntSushi was on the thread: https://github.com/rust-lang/libs-team/issues/923#issuecomment-6341922611

> This SGTM, but I remain opposed to adding the concept of day (and thus week) to std::time::Duration. Jiff specifically opts out of these concepts for its own SignedDuration.

Nia: I'd be open to adding the other ones (not days & weeks). But I'd also mention that we have constants for these.

Fon: They're unstable.

Nia: I propose we split these into two stabilization tracks (days & weeks is one and hours & minutes is the other one)

Fon: I think we have as for everything under the second level, this would add this for up to hours & minutes and possibly up to days and weeks. I'd suggest we split all of it (constants and functions) too. This is primarily asking for minutes and hours, we should split.

David: We might call them `nominal_days` etc. rather than regular days and that might be ok with Sushi

Nia: I like nominal_days. I'd like to have this API to exist.

Josh: Note that it's not just 23 hour or 25 hour days; some time zones have had 22, 21, 27, 48, or 0 hour days, for instance.

Amanieu: We don't need to add extra qualifiers.

Fon: Note that jiff doesn't have any form of days/weeks. I think the point is to pushing people to using calendar types when using days rather than having them in duration.

Nia: I'll reply with this and also add David's point. Should we mark the ACP accepted?

David: IIRC jiff has two different Durations (one is just nanosecond type and the other a tuple that's got days, seconds, hours). Is that something we considered?

Nia: I'd love do see a spelled out API for that.

Josh: I think there's potentially value in having the tuple of components type. But I don't think we should have API to turn that into a calendar interval because that needs a timezone database.

The 8472: Duration has no relation to calendar, wall time etc. It might be coming from anywhere.

David: The proposal is to add a second duration type.

Nia: There's a world where we expose something like what David's proposing. I could see that but someone would need to write up an ACP.

Josh: I'm normally a maximalist around adding things to stdlib. But my rationale about not adding a tz database is 1) that people care about where they get it (OS vs. something else). And the TZ database frequently ships critical updates on short notice (because some geopolitical region changes their time zone rules on short notice). I'd rather not have that.

David: Shipping a TZ database is not the only way to do this. We could provide the TZ interface and the ecosystem would provide the database.

Josh: That's what the vocabulary (tuple) suggestion could do

Fon: We could also offer whatever the system time representation is without depending on anything that can't be bundled in the standard library
